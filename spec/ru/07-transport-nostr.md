# 07. Транспорт Nostr

[English](../en/07-transport-nostr.md) · Русский

Снято с iOS `5b8efc8`. Это действующий частный формат Bitchat/Shum,
использующий события Nostr. Номера 1059/13/14 и префикс `v2:` не означают
совместимость с NIP-17, NIP-44 или NIP-59. Реализацию этих NIP нельзя
подставлять вместо описанного ниже шифрования.

## 1. Источники

В `Shum-iOS/ShumiOS/`:

- `Vendor/Nostr/NostrProtocol.swift`: `createPrivateMessage`,
  `decryptPrivateMessage`, `encryptContent`, `decryptContent`, `NostrEvent`.
- `Vendor/Nostr/NostrRelayManager.swift`: соединения, фильтры, подтверждения.
- `Vendor/Nostr/`: `NostrIdentity`, `NostrTransport`.
- `Vendor/Messaging/ShumNostrService.swift`: приём Shum, поиск карточек,
  ограничение очередей и сохранение обработанных событий.
- `Vendor/Messaging/ShumConversationStore.swift`: `ShumWireProtocol`.
- `Vendor/`: `XChaCha20Poly1305Compat`, `Base64URLCoding`.

Генератор: `ShumTests/Protocol/ShumProtocolVectorTests.swift`,
`nostrEnvelopes()`. Фикстуры: `07-events.json`, `07-private-envelopes.json`.

## 2. Событие и подпись

Поля объекта: `id`, `pubkey`, `created_at`, `kind`, `tags`, `content`,
необязательное `sig`. `created_at` представляет целые секунды Unix.
Публичный ключ: 32 байта x-only secp256k1, 64 символа hex.
Подпись BIP-340: 64 байта, 128 символов hex. `id`: SHA-256, 64 hex.

Вход SHA-256: компактный UTF-8 JSON массива

```text
[0,pubkey,created_at,kind,tags,content]
```

Порядок элементов обязателен. `/` не экранируется. Строки не нормализуются
в NFC. Здесь используется сериализация массива `JSONSerialization`, а не
канонический объект карточки из раздела 02. Фикстура содержит точные байты,
включая кириллицу, обратную косую черту, U+2028/U+2029 и управляющие символы.
Подписывается хеш, а не JSON непосредственно. iOS передаёт случайные
32 байта auxiliary randomness в Schnorr. При проверке пересчитывается `id`,
проверяются размеры и подпись относительно `pubkey`.

Декодер ограничивает число тегов 64, значений в теге 16, каждую строку тега
1024 байтами UTF-8. Порядок тегов и значений входит в подпись.

## 3. Три вложенных слоя

| Слой | kind | Автор | tags | content | Подпись |
|---|---:|---|---|---|---|
| rumor | 14 | настоящий отправитель | `[]` | исходная строка | отсутствует |
| seal | 13 | настоящий отправитель | `[]` | зашифрованный JSON rumor | BIP-340 |
| gift wrap | 1059 | новый случайный ключ | `[["p",recipient]]` | зашифрованный JSON seal | BIP-340 |

Rumor создаётся с текущим временем. Seal и wrap независимо получают
случайное время на 1–300 секунд раньше текущего. Для каждого wrap создаётся
новая secp256k1-личность. Ключ назначения у обоих шифрований один и тот же.
Значения `id` вложенных событий вычисляются обычным способом.

Приём строго в таком порядке:

1. Kind внешнего события равен 1059, теги точно совпадают с единственным
   `p` своего ключа, внешняя подпись верна.
2. Расшифровать content, декодировать seal: kind 13, tags пустые,
   обязательная корректная подпись.
3. Расшифровать content seal, декодировать rumor: kind 14, подписи нет,
   `pubkey` точно совпадает с подписавшим seal.
4. Rumor tags пустые либо точно `[["p",свойКлюч]]`. Второй вариант оставлен
   для совместимости со старым Android. Любые дополнительные теги запрещены.
5. Вернуть content rumor, **автора seal**, время rumor.

Нельзя принимать автора внешней обёртки за контакт. Сверка этого
аутентифицированного автора с карточкой описана в разделе 05.

## 4. Частное шифрование `v2:`

Используется тот же 32-байтовый секретный secp256k1-ключ, что у личности
Nostr. X-only ключ получателя поднимается в точку с чётным Y: префикс `02`
и 32 байта X. При отправке код также содержит fallback `03` при ошибке
построения публичного ключа.

ECDH в Swift вызывается с `format: .compressed`. Результат **33 байта**:
`02` или `03` плюс координата X точки `private × public`. Это не обычный
32-байтовый ECDH-хеш libsecp256k1 и не одна координата X.

```text
shared = compressedSEC1(private × public)       # 33 байта
key = HKDF-SHA256(ikm=shared, salt=пусто,
                  info=UTF8("nip44-v2"), length=32)
nonce = random(24)
(ciphertext,tag) = XChaCha20-Poly1305(key,nonce,plaintext,AAD=пусто)
content = "v2:" + base64url_no_padding(nonce || ciphertext || tag)
```

Нет нулевого байта в конце `info`. Salt не равен строке `nip44-v2`.
Нет версии, паддинга или MAC вне AEAD. Tag 16 байт. XChaCha: HChaCha20
с первыми 16 байтами nonce, затем ChaCha20-Poly1305 с nonce
`00000000 || nonce[16..24]`.

При расшифровании x-only ключ автора пробуется с префиксами `02`, затем
`03`: паритет исходного секретного ключа влияет на shared point.
Успех определяет проверка AEAD. Декодер Base64URL допускает также стандартные
`+`/`/`, добавляет недостающий padding. Передающая сторона использует URL-safe
алфавит без `=`.

Строка encrypted content ограничивается 64 KiB **до** base64-декодирования.
Combined должен иметь больше 40 байт: nonce24 + непустой cipher + tag16.
Расшифрованный вложенный JSON также ограничен 64 KiB. Plaintext должен быть
валидным UTF-8. Эти проверки повторяются для обоих слоёв.

## 5. Содержимое Shum

Строка rumor:

```text
"shum-v1:" + standard_base64(ShumCoding.encode(ShumPacket))
```

Принимается также `spotchat-v1:`. Это стандартный Base64, не Base64URL
внешнего cipher. JSON пакета ограничен 24 000 байтами; входная строка с
префиксом 33 000 байтами. После decoding применяются разделы 03–05.
Nostr не переносит внешний BLE hopCount как доказательство пути.

ShumNostrService не применяет собственный общий возрастной предел к rumor.
Сроки пакета проверяет обработчик конкретного вида. Нельзя переносить сюда
900-секундное окно соседних обработчиков Bitchat.

## 6. Релеи, подписка и подтверждения

Встроенный список на указанной ревизии:

```text
wss://nostr.oxtr.dev
wss://soloco.nl
wss://relay.snort.social
wss://nostr.bitcoiner.social
```

Пользовательские релеи добавляются отдельно. Это снимок конфигурации iOS,
не обещание доступности внешних серверов.

Подписка `shum-private-v1`:

```json
{"kinds":[1059],"#p":["свой-x-only-ключ"],"since":0,"limit":100}
```

`since` на практике равен now минус 3 суток в Unix seconds. Сообщение NIP-01:
`["REQ",subscriptionID,filter]`; публикация `["EVENT",event]`.
После восстановления соединения менеджер восстанавливает подписки.
`EOSE` означает конец сохранённой выдачи, а не доставку пользователю.

`sendShumPacket` использует немедленную отправку. Успех означает хотя бы
один `OK(eventID,true,...)` от релея до таймаута 10 секунд. Он переводит
сообщение в forwarding; только подписанный ShumReceipt означает delivered
или read. Очереди, повторные попытки и push описаны в разделах 05 и 08.
Для статуса Shum нужен подключённый DM-релей, не любой географический релей.

## 7. Дубли и ограничения приёма

Одновременно работают до 4 обработчиков, очередь до 128. Переполненная
очередь отбрасывает событие без пометки «обработано».
Быстрый набор seen имеет предел 1000. Дополнительный persistent handled
хранится 4 суток: целевой предел 30 000, при превышении 31 000 остаются
30 000 новейших. При загрузке очищаются просроченные записи.

Формат файла: последовательность записей 36 байт, каждая
`eventID[32] || handledUnixSeconds[4,BE]`, порядок не определён.
Сохранение откладывается на 2 секунды. Это незашифрованный индекс событий,
отдельный от SQLite. Ошибочно расшифрованное/недопустимое событие также
помечается обработанным. Дубли ShumEnvelope дополнительно проверяются
независимо от eventID обёртки: раздел 05.

## 8. Получение карточки по c2

Из c2 извлекается Nostr-ключ (раздел 02). Отправляется обычное личное
сообщение этим же трёхслойным способом. Форматы строк:

| Префикс | JSON после standard Base64 | Предел decoded |
|---|---|---:|
| `shum-contact-request-v1:` | `{"id":"uuid-lowercase"}` | 256 |
| `shum-contact-manifest-v1:` | `{"id":...,"card":...,"profile":...}` | 4096 |
| `shum-contact-chunk-v1:` | id, hash, offset, data | 6144 |

До 8 запросов одновременно, таймаут 20 секунд, поиск себя запрещён.
`id` должен разбираться как UUID; создаваемый id содержит 36 символов.
Lookup использует `sendEvent`, не ожидает relay OK как отправка сообщения.
Ответы одному ключу ограничены интервалом 3 секунды. Карта ограничителя
при 1000 ключах очищается от записей старше 300 секунд.

Ответ принимается только для ожидаемого id; ключ искомого контакта,
аутентифицированный автор seal и `card.nostrKey` должны совпадать.
Карточка и manifest валидируются. Имя, bio и avatarSeed manifest должны
точно совпасть с карточкой. Аватар рисуется локально из seed.
Фото и chunks текущий обработчик не принимает: наличие имён packet
не означает работающую передачу фото через Nostr.

## 9. Примеры и вопросы

`07-events.json` фиксирует байты хеширования, BIP-340 и фильтр подписки.
`07-private-envelopes.json` содержит настоящую обёртку, ключи получателя,
оба промежуточных shared/key/plaintext и отрицательные проверки.
Исторический единственный p-тег rumor принимается; лишний тег, чужой
получатель, неверные подписи и несовпадающий автор rumor отвергаются.
Проверки не подключаются к реальным релеям.

1. Нестандартное шифрование с именем `v2:` легко спутать с NIP-44. В v1
   воспроизводим именно его; переход на стандарт требует отдельного v2.
2. Открытый persistent event index раскрывает идентификаторы и время приёма.
   Формат хранения CLI может защищать его, не меняя сетевой v1.
3. Карточка без avatarSeed и manifest с fallback seed могут не пройти
   строгую сверку. Нужен отдельный тест со старой карточкой без расширения.
4. Список публичных релеев требует эксплуатационной проверки. Набор в
   спецификации фиксирует код, а не состояние сети.
