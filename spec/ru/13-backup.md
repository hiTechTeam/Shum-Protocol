# 13. Резервная копия профиля

[English](../en/13-backup.md) · Русский

Часть v1 stable. Решение владельца от 10 октября 2026: каждый клиент умеет создавать резервную копию и восстанавливать из неё профиль, и копия, созданная в одном клиенте, восстанавливается в любом другом. Формат реализуется один раз в Rust Shum-Core (раздел 12, пункт 3): `shum-core` шифрует и разбирает файл, `shum-store` выгружает и загружает профиль. Клиенты дают только интерфейс: выбор файла, ввод пароля, напоминания.

Нынешняя копия iOS (пункт 8) — снимок внутренних файлов приложения. Она не переносится между клиентами и остаётся читаемой только для переноса черновых профилей.

## 1. Зачем нужна копия

Копия переносит один профиль на новое устройство или возвращает его, если устройство потеряно или приложение удалено. В ней лежат закрытые ключи профиля, поэтому файл защищён паролем, который человек придумывает сам.

Копия не служит для работы с одним профилем на двух устройствах одновременно. Если восстановить профиль на втором устройстве, пока первым ещё пользуются, получатся два устройства с одинаковыми ключами и без собственных ключей устройств. Для нескольких устройств профиль привязывают (раздел 10). Клиент, восстанавливающий копию, **должен** сказать об этом до восстановления.

## 2. Файл

| Свойство | Значение |
| :--- | :--- |
| Расширение | `.shumbackup` |
| Тип | `application/octet-stream` |
| Имя по умолчанию | `Shum-<имя профиля>-<ГГГГ-ММ-ДД>.shumbackup` |
| Наибольший размер | 192 МиБ |

Устройство файла: 14 байт ASCII `SHUM-BACKUP-2` и перевод строки (`0x0A`), затем один JSON-объект в UTF-8 — заголовок. После заголовка ничего нет.

```json
{
  "version": 2,
  "createdAt": "2026-10-10T18:04:00Z",
  "profileName": "Руслан",
  "kdf": { "name": "PBKDF2-HMAC-SHA256", "salt": "<base64, 16 байт>", "iterations": 210000 },
  "cipher": "AES-256-GCM",
  "nonce": "<base64, 12 байт>",
  "ciphertext": "<base64, шифротекст и 16 байт тега>"
}
```

- `createdAt` — RFC 3339 в UTC с целыми секундами.
- `profileName` и `createdAt` из заголовка показываются до ввода пароля, чтобы человек выбрал нужный файл. Они не защищены от подмены. После расшифровки клиент **должен** брать значения из содержимого (пункт 4).
- base64 стандартный, с выравниванием (RFC 4648, раздел 4).
- Читатель **должен** отклонить незнакомые `version`, `kdf.name` или `cipher`, соль длиной не 16 байт, nonce длиной не 12 байт, число итераций вне диапазона 100 000–1 000 000 и файл больше наибольшего размера.

## 3. Пароль и шифрование

1. **Пароль.** Не короче 10 символов (расширенных графемных кластеров Unicode) и не длиннее 256 байт UTF-8 после нормализации. Пароль приводится к Unicode NFC и кодируется в UTF-8. Клиенты **не должны** сохранять пароль.
2. **Ключ.** `key = PBKDF2-HMAC-SHA256(password, salt, iterations, 32 байта)`. При создании берётся новая случайная соль и 210 000 итераций. PBKDF2 выбран потому, что он есть в браузерах через WebCrypto.
3. **Шифрование.** AES-256-GCM с новым случайным 12-байтным nonce и дополнительными данными — 13 байт ASCII `SHUM-BACKUP-2`. Открытый текст — содержимое (пункт 4) в виде JSON в UTF-8.
4. Неверный пароль и повреждённый файл неразличимы: в обоих случаях не сходится тег GCM. Клиенты показывают одно сообщение, например «Неверный пароль или файл повреждён».

## 4. Содержимое

```json
{
  "version": 2,
  "createdAt": "2026-10-10T18:04:00Z",
  "profile": { "name": "Руслан", "ownerID": "<Shum ID, 64 hex>" },
  "keys": { "noise": "<base64, 32>", "signing": "<base64, 32>", "nostr": "<base64, 32>" },
  "state": { "version": 1, "ownerID": "<Shum ID>", "...": "..." }
}
```

- `keys` — три закрытых ключа из раздела 01: Noise X25519, зерно Ed25519 (RFC 8032) и Nostr secp256k1.
- Ключ хранилища из раздела 09 **не** входит в копию. Он принадлежит одному устройству; при восстановлении создаётся новый случайный ключ хранилища.
- `state` — состояние базы из раздела 09 (`version` 1) со всеми корзинами профиля: своя карточка и её метаданные, контакты, запросы, беседы, сообщения, квитанции, встречи, сохранённые профили, заблокированные, ID удалённых сообщений, состояния приглашений, реакции, очереди отправки и старая история.
- Не входят, потому что принадлежат устройству, а не профилю: `relay` (конверты, которые устройство несёт для других) и `seenRelay` (отсев повторов при пересылке).
- Незнакомые поля **должны** сохраняться при выгрузке и загрузке (раздел 12, пункт 5).
- Записи и ключи устройств из раздела 10 в копию профиля не входят. После восстановления устройство создаёт свой ключ устройства; пока форматы раздела 10 не закреплены, восстановленное устройство считается единственным устройством профиля.

## 5. Восстановление

Клиент **должен** проверить до любой записи:

1. `ownerID` совпадает с Shum ID ключа `keys.noise` (раздел 01, пункт 2), и `state.ownerID` совпадает с ним же.
2. Своя карточка в `state` подписана ключом `keys.signing` и содержит открытые ключи всех трёх закрытых.
3. `keys.nostr` — допустимый закрытый ключ secp256k1.
4. `state` проходит проверки раздела 09, пункт 8.

Затем:

- Если на устройстве уже есть профиль с тем же `ownerID`, клиент **не должен** молча объединять их. Он спрашивает, заменить ли профиль; по умолчанию — отмена.
- Профиль создаётся как новый локальный профиль (раздел 12, пункт 6) с именем из содержимого. База шифруется новым ключом хранилища, закрытые ключи кладутся в системное хранилище ключей, как у нового профиля.
- Запись атомарна: появляется весь профиль или ничего не меняется.
- После восстановления клиент ничего не публикует сам, кроме того, что делает обычный запуск: подписки на релеях, регистрация push, очереди отправки.

## 6. Создание

- Копия всегда содержит полное текущее состояние; частичных копий нет.
- Клиент создаёт файл на устройстве и отдаёт его человеку: системное окно сохранения, загрузка в браузере, путь в CLI. Клиенты **не должны** сами никуда выгружать копии.
- Клиент может напоминать, что последняя копия давно не создавалась. Хранить можно только дату последней копии, но не пароль и не файл.

## 7. Интерфейс клиентов

| Клиент | Создание | Восстановление |
| :--- | :--- | :--- |
| CLI | `shum backup create <файл>` | `shum backup restore <файл>` и первым вариантом в `shum init` |
| Десктоп и браузер | Профиль → Резервная копия | «Восстановить из резервной копии» на первом экране |
| iOS и Android | Настройки → Резервная копия | «Восстановить из резервной копии» при регистрации |

## 8. Нынешняя копия iOS, версия 1 (перенос)

Черновое приложение iOS записывает `SHUM-BACKUP-1`, перевод строки и JSON-заголовок `{version: 1, createdAt, profileName, salt, iterations, ciphertext}`. Отличия от версии 2:

| Поле | Версия 1 |
| :--- | :--- |
| `createdAt` | Секунды с 1 января 2001 года (`Date` из Foundation по умолчанию) |
| `salt`, `ciphertext` | base64; `ciphertext` — nonce, шифротекст и тег вместе (`combined` из CryptoKit) |
| Дополнительные данные | ASCII `hiTeam.ShumiOS.backup.v1` |
| Ключ | PBKDF2-HMAC-SHA256, как в пункте 3, 210 000 итераций |

Содержимое — снимок внутренних файлов iOS: `LocalCards-v1/own.json`, `ShumProfiles/own.json`, `ShumConversations/state.enc` (состояние базы, зашифрованное ChaCha20-Poly1305 ключом хранилища) и значения связки ключей `noiseStatic`, `noiseSigning`, `localCardSigning`, `nostrIdentity`, `shumStorage` и другие.

- Клиенты **должны** записывать только версию 2.
- Shum-Core **может** читать версию 1, чтобы перенести черновые профили (раздел 12, пункт 8): взять ключи, расшифровать `state.enc` ключом `shumStorage` и дальше действовать по пункту 5.
- Открытый вопрос: какой из ключей, `noiseSigning` или `localCardSigning`, — ключ Ed25519 из раздела 01. Уточнить по исходникам iOS и примерам до реализации чтения версии 1.

## 9. Примеры

`vectors/13-backup.json` добавляется вместе с реализацией в Shum-Core: заданные пароль, соль и nonce с ожидаемыми ключом, файлом и содержимым; файл с неверным паролем; повреждённый тег; содержимое, у которого `ownerID` не совпадает с ключами; файл версии 1, созданный iOS.
