# 02. Карточка контакта и приглашения

Черновик. Источник: `ShumIdentityService.swift` (`ShumContactCard`,
`ShumContactLocator`, `ShumInvitationPayload`, `ShumCoding`,
`ShumIdentityService.card(...)`), `docs/seed-profile-protocol.md`.

Карточка контакта это публичная, подписанная информация о человеке: его
ключи, имя, «О себе» и пиксельный аватар. Закрытых данных в ней нет.

## 1. Поля

| Поле JSON | Тип | Обязательно | Ограничения |
|---|---|---|---|
| `version` | целое | да | ровно `1` |
| `noiseKey` | байты, в JSON base64 | да | 32 байта, не все нули. Публичный Noise-ключ |
| `signingKey` | байты, в JSON base64 | да | 32 байта. Публичный Ed25519-ключ |
| `nostrKey` | строка | да | 64 строчных hex-символа. Публичный Nostr-ключ (x-only) |
| `name` | строка | да | после обрезки пробелов и переводов строк не пустое; не больше 64 байт UTF-8 |
| `bio` | строка | да | «О себе». Не больше 72 символов (см. вопрос 3) и не больше 640 байт UTF-8. Может быть пустой |
| `signature` | байты, в JSON base64 | да, может быть пустым | подпись карточки, 64 байта или пусто |
| `avatarSeed` | целое без знака, 64 бита | нет | семя пиксельного аватара |
| `avatarVersion` | целое | нет | версия генератора аватара, сейчас `1` |
| `avatarSeedSignature` | байты, в JSON base64 | нет | подпись семени, 64 байта |
| `profileRevision` | целое без знака, 64 бита | нет | номер ревизии профиля, больше 0 |
| `profileSignature` | байты, в JSON base64 | нет | подпись профиля, 64 байта |

Производные значения, которые в карточку **не** записываются:

- `id` это Shum ID, `hex(SHA-256(noiseKey))` (раздел 01);
- `peerID` это `hex(noiseKey)` (раздел 01);
- `profileID` это `hex(SHA-256(profile_bytes))`, см. ниже.

## 2. Канонический JSON

Все три подписи ставятся над JSON-представлением карточки. Подпись верна,
только если байты JSON совпадают побайтно, поэтому формат обязателен.

**Сейчас в iOS** JSON делает `JSONEncoder` от Apple с настройками
`.sortedKeys` и `.withoutEscapingSlashes` (`ShumCoding.encode`). Это даёт:

1. Объект без пробелов и переводов строк.
2. Ключи по возрастанию. Для имён полей карточки порядок такой:
   `avatarSeed`, `avatarSeedSignature`, `avatarVersion`, `bio`, `name`,
   `noiseKey`, `nostrKey`, `profileRevision`, `profileSignature`, `signature`,
   `signingKey`, `version`.
3. Поля со значением «нет» (`nil`) **не пишутся** вообще.
4. Байты пишутся строкой base64 со стандартным алфавитом и дополнением `=`.
   Пустые байты пишутся как `""`.
5. Целые пишутся десятичным числом без дробной части и без кавычек, включая
   значения больше 2^53 (у `avatarSeed` они бывают часто).
6. Строки пишутся в UTF-8 как есть. Экранируются только:

   | Символ | Как пишется |
   |---|---|
   | `"` | `\"` |
   | `\` | `\\` |
   | U+0008, U+000C, U+000A, U+000D, U+0009 | `\b`, `\f`, `\n`, `\r`, `\t` |
   | остальные U+0000–U+001F | `\u00XX`, hex строчными буквами, например `\u001f` |

   Всё остальное пишется как есть, без экранирования: `/`, U+007F, U+2028,
   U+2029, кириллица, эмодзи. Это подтверждено тестовым примером
   `control-and-separators` в `vectors/02-canonical-json.json`.

Пример формы (значения сокращены):

```json
{"bio":"Барба это жызн!","name":"Игорь Загоев","noiseKey":"q2…=","nostrKey":"7f3a…","signature":"","signingKey":"Zx…=","version":1}
```

## 3. Три подписи

Все подписи ставятся ключом `signingKey` (Ed25519).

### 3.1. Подпись карточки, поле `signature`

Самая старая подпись. Покрывает только ключи, имя и «О себе».

```text
card_bytes = canonical_json( карточка, где
                 signature            = пусто ("")
                 profileRevision      = нет
                 profileSignature     = нет
                 avatarSeed           = нет
                 avatarVersion        = нет
                 avatarSeedSignature  = нет )
signature  = Ed25519.sign( signing_private_key, card_bytes )
```

Метки домена нет. Это сохранено для старых версий Shum и для push-сервера
(раздел 08). Ключи в `card_bytes` идут в порядке: `bio`, `name`, `noiseKey`,
`nostrKey`, `signature`, `signingKey`, `version`.

В коде: `signedBytes()`.

### 3.2. Подпись семени аватара, поле `avatarSeedSignature`

```text
seed_bytes = "shum.avatar-seed.v1\0"            // 20 байт
             || noiseKey                         // 32 байта
             || avatarSeed как UInt64 little-endian  // 8 байт
avatarSeedSignature = Ed25519.sign( signing_private_key, seed_bytes )
```

`seed_bytes` существует, только если есть `avatarSeed` и `avatarVersion == 1`.
Иначе подписывать и проверять нечего.

В коде: `avatarSeedBytes()`.

### 3.3. Подпись профиля, поле `profileSignature`

Новая подпись. Покрывает весь публичный профиль: ключи, имя, «О себе», семя
аватара, версию генератора и ревизию.

```text
profile_bytes = "shum.profile.v1\0"          // 16 байт
                || canonical_json( карточка, где
                       signature            = пусто ("")
                       avatarSeedSignature  = нет
                       profileSignature     = нет )
profileSignature = Ed25519.sign( signing_private_key, profile_bytes )
profileID        = hex( SHA-256( profile_bytes ) )
```

`profileID` не зависит от случайности подписей, поэтому по нему сравнивают
содержимое профилей.

В коде: `profileBytes()`, `profileID`.

## 4. Проверка карточки

Совместимый клиент **должен** проверять каждую полученную карточку по этим
правилам (в коде `validate()`). Нарушение любого правила означает, что
карточка недействительна.

Общие правила:

1. `version == 1`.
2. `noiseKey` 32 байта и не все нули; `signingKey` 32 байта.
3. `nostrKey` ровно 64 символа `[0-9a-f]` (вопрос 1).
4. `name` после обрезки пробелов и переводов строк не пустой, `name` не длиннее 64 байт UTF-8.
5. `bio` не длиннее 72 символов и не длиннее 640 байт UTF-8.
6. `signingKey` принимается как публичный ключ Ed25519.

Дальше два варианта.

**Вариант А: есть `profileRevision`** (современная карточка):

1. `profileRevision > 0`, есть `avatarSeed`, `avatarVersion == 1`.
2. `profileSignature` 64 байта и верна для `profile_bytes`.
3. Если `signature` не пустая, она должна быть верна для `card_bytes`.
4. Если есть `avatarSeedSignature`, она должна быть 64 байта и верна для `seed_bytes`.

Пустая `signature` и отсутствие `avatarSeedSignature` в этом варианте
допустимы: так выглядит карточка, полученная из QR-кода `c4`.

**Вариант Б: нет `profileRevision`** (старая карточка):

1. `profileSignature` отсутствует.
2. `signature` 64 байта и верна для `card_bytes`.
3. Если есть `avatarSeed`: `avatarVersion == 1`, `avatarSeedSignature` 64 байта и верна для `seed_bytes`.
4. Если `avatarSeed` нет, то `avatarVersion` и `avatarSeedSignature` тоже должны отсутствовать.

## 5. Как приложение создаёт свою карточку

Порядок в `ShumIdentityService.card(name:bio:avatarSeed:revision:)`:

1. Заполнить ключи, `name`, `bio` (обрезанный до 72 символов), `version = 1`.
2. Подписать `card_bytes`, записать в `signature`.
3. `avatarSeed` = выбранное семя или семя по умолчанию из Noise-ключа (раздел 01),
   `avatarVersion = 1`.
4. Подписать `seed_bytes`, записать в `avatarSeedSignature`.
5. `profileRevision` = переданная ревизия, по умолчанию `1`.
6. Подписать `profile_bytes`, записать в `profileSignature`.
7. Проверить карточку по разделу 4.

Итог: карточка, созданная приложением, всегда содержит все шесть
необязательных полей.

## 6. Какая карточка новее

Когда о человеке пришла карточка, а у нас уже есть другая, побеждает одна из
них (в коде `preferred(over:)`):

1. Новая карточка должна пройти проверку.
2. Ключи обеих карточек (`noiseKey`, `signingKey`, `nostrKey`) должны совпадать.
   Если не совпадают, это другой человек, новая карточка отклоняется.
3. Сравниваются ревизии (`profileRevision`, отсутствие считается за `0`).
   Большая побеждает.
4. Если ревизии равны и больше `0`:
   - если `profileID` разные, побеждает карточка с большим `profileID` при
     сравнении строк hex;
   - если `profileID` одинаковые, побеждает та, у которой больше
     дополнительных подписей (`signature` и `avatarSeedSignature`). При
     равенстве остаётся старая.
5. Если обе ревизии `0` (старые карточки), побеждает новая.

Пункт 4 нужен, чтобы два устройства после восстановления из резервной копии
пришли к одному результату без переговоров.

## 7. Приглашения

Карточку передают ссылкой или QR-кодом. Все ссылки не длиннее 4096 байт.

### 7.1. `shum://c4/<данные>` — основной формат

Создаётся сейчас для QR-кода профиля и для «Поделиться». Данные это двоичная
строка в base64url без дополнения:

| Смещение | Размер | Поле | Порядок байтов |
|---|---|---|---|
| 0 | 1 | формат = `4` | |
| 1 | 1 | `version` карточки | |
| 2 | 32 | `noiseKey` | |
| 34 | 32 | `signingKey` | |
| 66 | 32 | `nostrKey` в виде байтов | |
| 98 | 1 | длина `name` в байтах, N | |
| 99 | N | `name`, UTF-8 | |
| 99+N | 2 | длина `bio` в байтах, M | big-endian |
| 101+N | M | `bio`, UTF-8 | |
| 101+N+M | 8 | `avatarSeed` | little-endian |
| 109+N+M | 1 | `avatarVersion` | |
| 110+N+M | 8 | `profileRevision` | little-endian |
| 118+N+M | 64 | `profileSignature` | |

Полей `signature` и `avatarSeedSignature` в `c4` нет: подпись профиля уже
покрывает всё. Получатель восстанавливает карточку с пустой `signature` и без
`avatarSeedSignature` (вариант А раздела 4).

Если у карточки нет семени, ревизии или подписи профиля, вместо `c4`
создаётся старый формат `c`.

QR-код строится с коррекцией ошибок уровня M, чтобы читался с логотипом в центре.

### 7.2. `https://<сервер>/invite#c4/<данные>` — ссылка для мессенджеров

Та же строка `c4`, но в виде HTTPS-ссылки, которую распознают мессенджеры.
Данные лежат во **фрагменте** после `#`, поэтому при открытии страницы они не
уходят на сервер.

Разбор: схема `https`, путь ровно `/invite`, фрагмент читается как
`shum://<фрагмент>` и разбирается заново.

Сервер берётся из настройки приложения `ShumPushAPIBaseURL`.

### 7.3. Старые форматы, которые нужно уметь читать

| Ссылка | Формат | Что внутри |
|---|---|---|
| `shum://c/<данные>` | двоичный, байт формата `1` | как `c4` до `bio` включительно, затем `signature` (64 байта). Без семени и ревизии |
| `shum://c3/<данные>` | двоичный, байт формата `3` | как `c4` до `bio` включительно, затем `signature` (64), `avatarSeed` (8, LE), `avatarVersion` (1), `profileRevision` (8, LE), `avatarSeedSignature` (64), `profileSignature` (64) |
| `shum://c2/<43 символа>` | только ключ | base64url от 32 байт Nostr-ключа. Карточку нужно найти через Nostr (раздел 07) |
| `shum://contact?data=<base64>` | JSON | карточка в JSON, base64 со стандартным алфавитом в параметре `data` |

Создавать эти форматы новым клиентам **не нужно**, кроме `c`, который
создаётся как запасной вариант (раздел 7.1).

### 7.4. Правила разбора двоичных форматов

1. Схема `shum`, хост `c`, `c3` или `c4`.
2. Путь без начальных и конечных `/` не пустой и не длиннее 2048 байт.
3. Заменить `-` на `+`, `_` на `/`, дописать `=` до длины, кратной 4,
   раскодировать base64. Результат не длиннее 1536 байт.
4. Первый байт должен совпасть с хостом: `c4` → `4`, `c3` → `3`, `c` → `1`.
5. Прочитать поля по таблице формата. Если данных не хватает, ссылка
   недействительна.
6. После последнего поля **не должно** остаться ни одного байта.
7. `name` и `bio` должны быть правильным UTF-8.
8. Собранная карточка должна пройти проверку раздела 4.

Для `c2`: путь ровно 43 символа, после добавления одного `=` раскодируется в
32 байта, которые должны дать 64 строчных hex-символа.

Для `contact`: значение `data` раскодируется в не больше 2048 байт и читается
как JSON карточки (байты в base64), затем проверка раздела 4.

## Вопросы

1. **Шестнадцатеричные цифры в `nostrKey`.** Swift проверяет символы через
   `Character.isHexDigit`, а это `true` и для полноширинных цифр и букв
   (`０`–`９`, `ａ`–`ｆ`). Значит, Swift пропустит в `nostrKey` такие символы,
   хотя дальше превратить их в байты не сможет. **Подтверждено** примером
   `nostr-key-fullwidth-a` в `vectors/02-validate.json`: Swift такую карточку
   принимает. Спецификация требует только ASCII `[0-9a-f]`. **Исправлено** в
   Shum-iOS коммитом `5b8efc8`. Пример перегенерирован: `swift_valid: false`.
2. **Канонический JSON зависит от Apple.** Формат подписываемых байтов
   определяется поведением `JSONEncoder`. Правила экранирования и порядок
   ключей теперь записаны и подтверждены примерами, но они остаются чужой
   реализацией: если Apple изменит `JSONEncoder` в новой iOS, подписи старых
   карточек перестанут сходиться. Переход на двоичный формат в v2 (CBOR или
   Protobuf, раздел 2 ROADMAP) снимает этот риск.
3. **Длина «О себе» в символах.** Ограничение 72 считается в графемах Swift
   (`String.count`). Число графем зависит от версии таблиц Unicode, например
   для новых эмодзи. Rust-клиент с другой версией Unicode может принять или
   отклонить ту же строку иначе. Предложение для v2: считать только байты.
4. **Какие пробелы обрезаются в `name`.** Swift использует
   `CharacterSet.whitespacesAndNewlines`. Перебор всех Unicode scalars на
   разрешённом симуляторе дал: U+0009–000D, U+0020, U+0085, U+00A0,
   U+1680, U+2000–200B, U+2028–2029, U+202F, U+205F, U+3000.
   Этот набор явно записан в Rust; U+200B включён, хотя Rust `is_whitespace`
   его не включает. Фикстура `02-foundation-ed25519.json`.
5. **Строгость проверки Ed25519.** CryptoKit и Rust-библиотеки (например
   `ed25519-dalek` в обычном и строгом режиме) по-разному относятся к
   некоторым краевым ключам и подписям. Нужно выбрать режим и проверить его
   на подписях, сделанных в Swift. Новые граничные примеры подтверждают:
   CryptoKit принимает identity public/R с S=0 и zero public/R с S=0
   для зафиксированного сообщения. Неканонические public и S отвергаются.
   Rust `verify_strict` принимает все настоящие подписи и отвергает эти
   вырожденные варианты. Рекомендация: строгий режим с явным исключением
   совместимости; решение запрошено у владельца, пока не согласовано.
6. **Подпись карточки без метки домена.** Подпись `signature` ставится над
   JSON без метки домена. Пока JSON начинается с `{`, перепутать её с другими
   подписями нельзя. В v2 у неё тоже должна появиться метка.
