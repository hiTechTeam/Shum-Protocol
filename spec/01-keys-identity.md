# 01. Ключи и личность

Черновик. Источник: `ShumIdentityService.swift`, `NoiseEncryptionService.swift`,
`NostrIdentity.swift`, `NostrIdentityBridge.swift`, `ShumPixelAvatarGenerator.swift`,
`BitFoundation/PeerID.swift`.

## 1. Три пары ключей

Личность Shum состоит из трёх независимых пар ключей. Все три создаются
случайно при первом запуске, **ни одна не выводится из другой**.

| Ключ | Алгоритм | Закрытый | Публичный | Для чего |
|---|---|---|---|---|
| Noise | X25519 (Curve25519 Diffie–Hellman) | 32 байта | 32 байта | шифрование: Noise-сессии по Bluetooth и запечатывание конвертов. От него считается Shum ID |
| Подпись | Ed25519 | 32 байта (seed по RFC 8032) | 32 байта | подпись карточки, профиля, семени аватара и пакетов |
| Nostr | secp256k1, подписи Schnorr по BIP-340 | 32 байта | 32 байта, x-only | подпись событий Nostr, адрес на релеях |

Публичный ключ Nostr показывается людям ещё и в формате `npub` (Bech32 с
префиксом `npub`), но в протоколе передаётся как 64 hex-символа.

**Сейчас в iOS** ключи лежат в Keychain:

| Ключ | Где |
|---|---|
| Noise, закрытый | `noiseStaticKey` |
| Подпись, закрытый | `ed25519SigningKey` |
| Nostr | сервис `chat.shum.nostr`, ключ `nostr-current-identity`, JSON `{privateKey, publicKey, npub}`, где `privateKey` и `publicKey` в base64 |

Совместимому клиенту формат хранения не важен. Важно только, что закрытые
ключи не покидают устройство.

### Подписи Ed25519 не детерминированы

CryptoKit подписывает Ed25519 со случайной добавкой: одна и та же подпись,
сделанная дважды, даёт разные 64 байта. Обе подписи проверяются стандартной
проверкой RFC 8032. Поэтому:

- совместимый клиент **должен** проверять подписи стандартно, а не сравнивать байты;
- совместимый клиент **может** подписывать детерминированно по RFC 8032;
- тестовые примеры для подписей проверяют только «подпись верна».

## 2. Shum ID

Shum ID это основной идентификатор человека в протоколе.

```text
shum_id = hex( SHA-256( noise_public_key ) )
```

- `noise_public_key` это 32 байта публичного Noise-ключа.
- Результат: 64 строчных hex-символа.
- В коде: `ShumContactCard.userID(_:)`, свойство `ShumContactCard.id`.

Та же функция применяется и к другим данным, например к байтам профиля
(см. `profileID` в разделе 02). Имя функции в коде общее, но Shum ID это
только хэш Noise-ключа.

## 3. ID собеседника для Bluetooth

Для маршрутизации в Bluetooth-сетке собеседник с известной карточкой
адресуется своим полным Noise-ключом:

```text
peer_id = hex( noise_public_key )        // 64 строчных hex-символа
```

В коде: `ShumContactCard.peerID`, `PeerID(hexData:)`.

Bitchat внутри сетки использует ещё и короткие 8-байтовые ID (16 hex-символов),
которые меняются со временем. Они относятся к транспорту и описаны в
разделе 06.

## 4. Семя пиксельного аватара

У каждой личности есть пиксельный аватар, который рисуется из 64-битного
семени (seed). По умолчанию семя выводится из Noise-ключа:

```text
digest = SHA-256( "shum.pixel-avatar.v1\0" || noise_public_key )
seed   = UInt64 из digest[0..8], little-endian
```

- `"shum.pixel-avatar.v1\0"` это 21 байт: ASCII-текст и нулевой байт.
- Человек может выбрать другой вариант аватара («другой вариант» в приложении).
  Тогда семя случайное и передаётся в карточке (поле `avatarSeed`).
- Рисование по семени (генератор, палитра, правила) это отдельный контракт
  совместимости, он описывается в приложении к спецификации. Номер генератора
  передаётся в поле `avatarVersion`, сейчас `1`. Неизвестную версию клиент
  должен отклонять, а не рисовать как получится.

В коде: `ShumPixelAvatarGenerator.seed(for:)`, `ShumPixelAvatarGenerator.version`.

## 5. Метки домена

Все подписи в Shum ставятся над данными с меткой домена в начале. Метки
известные на сейчас:

| Метка | Байт | Где используется |
|---|---|---|
| `shum.pixel-avatar.v1\0` | 21 | вывод семени аватара (не подпись, хэш) |
| `shum.avatar-seed.v1\0` | 20 | подпись семени аватара |
| `shum.profile.v1\0` | 16 | подпись профиля |

Подпись карточки (поле `signature`) метки домена **не** имеет. Это наследие
первой версии, см. раздел 02.

Список будет дополнен метками из разделов 03 и 04.

## 6. Ключ локального хранилища

У приложения есть ещё четвёртый ключ: 32 случайных байта для шифрования базы
на устройстве (Keychain `shumStorageKey`, раньше `spotchatStorageKey`). Он не
участвует в протоколе и никуда не передаётся. Упоминается здесь, чтобы не
путать его с ключами личности.

## 7. Производные личности Nostr из Bitchat

В коде Bitchat есть личности Nostr, выведенные из общего семени устройства:
для геохэшей (`deriveIdentity(forGeohash:)`) и для мостов
(`deriveIdentity(forBridgeRendezvous:)`). К карточке и переписке Shum они не
относятся. Нужно ли их описывать, см. вопросы.

## Вопросы

1. **Производные личности Nostr.** Используются ли геохэши и мосты Bitchat в
   Shum 1.0? Если нет, их стоит явно исключить из v1.
2. **Связь Noise-ключа и Nostr-ключа.** Они независимы, а связь между ними
   держится только на подписанной карточке. В Bitchat есть ещё таблица
   `nostr-noise-<base64>` в Keychain. Нужно проверить, используется ли она в Shum.
3. **Смена ключей.** Сейчас ключи живут всё время жизни профиля, смены нет.
   Если ключ утёк, единственный выход это новый профиль. Это нужно записать в
   v2 вместе с ratchet.
