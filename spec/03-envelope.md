# 03. Конверт сообщения

Черновик v1. Снято с Shum-iOS `5b8efc8` и Bitchat из
`Upstreams/versions.json`, ревизия `9b84b361225facd8e623f25d76f889d3dc54a879`.

Источники в `Shum-iOS/ShumiOS/`:

- `Vendor/Messaging/ShumConversationStore.swift`: `ShumEnvelope`,
  `ShumPlaintext`, `ShumReplyReference`, `ShumConversation.identifier`.
- `Vendor/Messaging/ShumMessageStore.swift`: `send`, `receive`, `accept`,
  `carry`, `routeOutbox`, `routeRelay`, `makeReceipt`.
- `Vendor/Messaging/ShumIdentityService.swift`: `ShumCryptoService`, `ShumCoding`.
- `Vendor/Bluetooth/Services/BLE/BLEService.swift`: `sealShumPayload`,
  `openShumPayload`, `sendShumPacket`.
- `Vendor/Bluetooth/Services/NoiseEncryptionService.swift`:
  `sealCourierPayload`, `openCourierPayload`.
- `Vendor/Bluetooth/Noise/NoiseProtocol.swift`: `NoiseHandshakeState`,
  `NoiseSymmetricState`, `NoiseCipherState`, `NoisePattern.messagePatterns`.

## 1. Слои

```text
ShumPlaintext JSON
  → Noise X на постоянный Noise-ключ получателя
  → ciphertext в подписанном ShumEnvelope
  → envelope в ShumPacket
  → Bluetooth Noise XX или зашифрованные слои Nostr
```

Таким образом, сообщение внутри Nostr шифруется и как Shum-конверт, и
как содержимое Nostr. Курьер проверяет подпись конверта, но не может открыть
текст. Одно и то же подписанное содержимое отправляется повторно по обоим
транспортам. Внешние транспортные упаковки могут меняться.

## 2. Поля ShumEnvelope

Все поля обязательны. Это JSON по правилам раздела 02: UTF-8, сортировка
ключей, без пробелов, `Data` в стандартном base64 с `=`, целые без дробей.

| Поле | Тип | Значение / проверка |
|---|---|---|
| `version` | целое | Ровно 1 |
| `id` | строка | UUID, принимаемый `UUID(uuidString:)` |
| `conversationID` | строка | Выводится из ID двух участников, см. ниже |
| `sender` | карточка | Полная подписанная карточка отправителя |
| `recipient` | карточка | Подписанная карточка получателя |
| `timestamp` | Int64 | Миллисекунды Unix, не меньше 0 |
| `expiresAt` | Int64 | Миллисекунды Unix, время истечения |
| `hopLimit` | целое | От 1 до 4 включительно, при создании 4 |
| `ciphertext` | Data | Не пусто, не больше 12 000 байт после base64-декодирования |
| `signature` | Data | Ed25519-подпись отправителя |

Порядок ключей: `ciphertext`, `conversationID`, `expiresAt`, `hopLimit`,
`id`, `recipient`, `sender`, `signature`, `timestamp`, `version`.
Вложенные карточки кодируются полностью по разделу 02, включая их подписи.

```text
conversationID = hex(SHA256(UTF8(sort([sender.id, recipient.id]).join(":"))))
digest         = hex(SHA256(ciphertext))
```

Сортировка применяется к двум строкам Shum ID. Они состоят из 64 ASCII
hex-символов, поэтому двоичная лексикографическая сортировка даёт тот же
результат, что Swift. Разделитель ровно один байт `3a`. `digest` вычисляется
по сырым байтам шифротекста, не по base64. Он не является полем конверта.

UUID при создании берётся из `UUID().uuidString` (обычно заглавные буквы).
При чтении регистр строки не меняют: текстовый ID также входит в подпись,
проверку внутреннего сообщения и ключи удаления/дедупликации.

## 3. Подпись и срок жизни

```text
unsigned = envelope с signature = пустые Data, то есть JSON-строка ""
signing_bytes = canonical_json(unsigned)
signature = Ed25519.sign(sender.signing_private_key, signing_bytes)
```

Метки домена у подписи конверта **нет**. Нельзя добавлять её в v1.
Подпись покрывает обе карточки, шифротекст, ID, время и `hopLimit`.

`validate(at:)` сначала проверяет обе карточки, затем все условия:

1. `version == 1`, ID является UUID, `sender.id != recipient.id`.
2. `conversationID` совпадает с вычисленным значением.
3. `timestamp >= 0` и `timestamp <= now_ms + 300_000`.
4. `expiresAt > now_ms`, `expiresAt > timestamp`.
5. `expiresAt - timestamp <= 86_400_000` (24 часа).
6. `hopLimit` в диапазоне 1…4, длина `ciphertext` в диапазоне 1…12 000.
7. Подпись верна для `sender.signingKey` и `signing_bytes`.

Границы времени включительные только там, где указано `<=`: конверт,
истекающий ровно сейчас, уже недействителен. Создающий код задаёт
`expiresAt = timestamp + 86_400_000`. Исторические сообщения хранятся и
после истечения: срок ограничивает приём и доставку, а не историю.

`validate` не вскрывает шифротекст. Подписанный произвольный массив из
12 000 байт может пройти эту функцию, но должен быть отклонён при вскрытии
у получателя. Эти проверки нельзя объединять в один неверный тест.

## 4. Внутреннее сообщение ShumPlaintext

| Поле | Тип | Содержание |
|---|---|---|
| `protocolName` | строка | Создаётся `shum.message.v1`, принимается также `spotchat.message.v1` |
| `id` | строка | В точности `envelope.id` |
| `conversationID` | строка | В точности `envelope.conversationID` |
| `senderID` | строка | В точности `envelope.sender.id` |
| `recipientID` | строка | ID текущего получателя |
| `timestamp` | Int64 | В точности `envelope.timestamp` |
| `expiresAt` | Int64 | В точности `envelope.expiresAt` |
| `text` | строка | Не пустая, не больше 4096 байт UTF-8 |
| `reply` | объект, необязателен | Отсутствует при `nil`, см. ниже |

`reply` содержит обязательные строки `messageID`, `senderID`, `text`.
`messageID` не пустой, до 255 байт UTF-8; UUID для него **не требуется**.
`text` не пустой, до 4096 байт. `senderID` равен ID одного из двух участников.
Это цитата-снимок; проверка существования исходного сообщения не проводится.

Отправляющий код обрезает текст через `.whitespacesAndNewlines` и проверяет
4096 байт. Принимающий код текст не обрезает: непустая строка из пробелов
сама по себе проходит его проверку. Подпись и шифрование относятся к
исходным байтам UTF-8 без нормализации Unicode.

## 5. Курьерская упаковка Noise X

### 5.1. Набор алгоритмов

| Параметр | Точные байты / алгоритм |
|---|---|
| Имя протокола | ASCII `Noise_X_25519_ChaChaPoly_SHA256` (31 байт) |
| Пролог | ASCII `bitchat-courier-v1` (18 байт), **без нулевого байта** |
| DH | X25519, статические и эфемерные ключи по 32 байта |
| AEAD | ChaCha20-Poly1305, ключ 32, nonce 12, tag 16 байт |
| Хэш и HKDF | SHA-256, HMAC-SHA256 |
| Premessage | Публичный статический ключ получателя `rs` |
| Единственное сообщение | `→ e, es, s, ss, payload` |

`sealCourierPayload` создаёт свежий `NoiseHandshakeState` на каждый конверт.
Он получает статический Noise-ключ отправителя, известный Noise-ключ
получателя и случайный эфемерный X25519-ключ. `openCourierPayload` создаёт
новый responder с постоянным ключом получателя и возвращает текст вместе
с аутентифицированным статическим ключом отправителя.

### 5.2. Инициализация и HKDF

```text
h  = UTF8(protocol_name) || 00       # дополнение имени до 32 байт
ck = h
h  = SHA256(h || UTF8("bitchat-courier-v1"))
h  = SHA256(h || rs)
```

Общие операции реализации:

```text
MixHash(data): h = SHA256(h || data)
HKDF2(ck, ikm):
    prk = HMAC_SHA256(key=ck, data=ikm)
    t1  = HMAC_SHA256(key=prk, data=01)
    t2  = HMAC_SHA256(key=prk, data=t1 || 02)
    return (t1, t2)
MixKey(ikm): (ck, k) = HKDF2(ck, ikm); nonce_counter = 0
```

У HKDF нет строкового `info`. Это Noise HKDF с байтовыми счётчиками `01`,
`02`, не произвольный вызов HKDF с другой меткой домена.

### 5.3. Порядок построения

1. Записать публичный эфемерный ключ `e` (32 байта), `MixHash(e)`.
2. Вычислить `es = X25519(ephemeral_private_sender, rs)`, `MixKey(es)`.
3. Зашифровать статический публичный ключ отправителя `s` с AEAD-ключом `k`,
   AAD = текущий `h`, nonce = `00 00 00 00 || LE64(0)`.
   Записать `encrypted_s || tag` (48 байт), `MixHash` этих 48 байт.
4. Вычислить `ss = X25519(static_private_sender, rs)`, `MixKey(ss)`.
   Это снова сбрасывает nonce в 0.
5. Зашифровать JSON `ShumPlaintext` с новым `k`, AAD = текущий `h`,
   nonce = `00 00 00 00 || LE64(0)`. Записать `encrypted_payload || tag`.
   Выполнить `MixHash` последних байт.

### 5.4. Формат результата

| Смещение | Размер | Поле |
|---|---|---|
| 0 | 32 | Публичный эфемерный X25519-ключ |
| 32 | 32 | Зашифрованный статический публичный ключ отправителя |
| 64 | 16 | Poly1305 tag статического ключа |
| 80 | P | Зашифрованный payload |
| 80+P | 16 | Poly1305 tag payload |

Итого `P + 96` байт. Нет байта версии, длины, nonce или префикса типа.
В отличие от транспортного Noise XX здесь **нет 4-байтового счётчика**.
Даже пустой payload имеет 96 байт результата.

Открывающий код читает первые 32 байта как `e`, выполняет `es` со своим
статическим приватным ключом, открывает 48 байт `s`, затем выполняет `ss`
и открывает оставшийся payload. Обе AEAD-проверки обязательны.
Полученный `s` должен совпасть с `envelope.sender.noiseKey`.

### 5.5. Проверка X25519-ключей

`NoiseHandshakeState.validatePublicKey` требует ровно 32 байта и отклоняет
следующие сырые представления (сравниваются все байты):

- `00` × 32;
- `01 || 00` × 31;
- `00` × 31 `|| 01`;
- `e0eb7a7c3b41b8ae1656e3faf19fc46ada098deb9c32b1fd866205165f49b800`;
- `5f9c95bca3508c24b1d0b1559c83ef5b04445cc4581c8e86d8224eddd09f1157`;
- `ff` × 32;
- `da || ff` × 31;
- `db || ff` × 31.

После этого создаётся ключ CryptoKit и выполняется DH. Совместимый клиент
должен также отклонять нулевой общий секрет. Эта проверка транспорта строже
проверки `noiseKey` в карточке, где явно запрещён только полностью нулевой
ключ. Нельзя считать принятую карточку доказательством допустимости DH.

## 6. Получатель, пересылки и дубли

До расшифрования получатель проверяет конверт и все три публичных ключа
своей карточки. По Nostr аутентифицированный внешний отправитель должен
совпасть с `envelope.sender.nostrKey`.

`hopCount` находится в `ShumPacket` и подписью конверта **не покрывается**.
Отправляющий узел ставит 1 для первой Bluetooth-передачи, каждый курьер
прибавляет 1. Получатель по BLE требует `1 <= hopCount <= hopLimit`.
Курьер сохраняет только `1 <= hopCount < hopLimit`. При приёме через
Nostr проверка `hopCount` пропускается; в истории записывается 0.

Курьер проверяет аутентифицированную BLE-личность депонента. На устройстве
не больше 64 курьерских конвертов, 8 от одного депонента и 4000 ID в
`seenRelay`. За одну цепочку узел предлагает конверт не больше чем трём
разным курьерам. Подробнее очереди и повторов в разделе 05.

Для уже сохранённого входящего сообщения с тем же ID, отправителем и
`digest` повторно открыть текст не требуется. Получатель повторяет ACK,
если контакт всё ещё допущен к переписке. Другой digest с тем же ID
отклоняется. ID с активной записью удаления не принимается. Отметка
от релея о приёме события не означает доставку получателю.

## Вопросы

1. **Отсутствие forward secrecy у курьерского конверта.** Компрометация
   постоянного Noise-ключа получателя раскрывает ранее перехваченные
   конверты. Поверх BLE XX это не отменяет свойств самого Noise X.
   Prekey-варианты в Bitchat существуют, но `sealShumPayload` для Shum
   использует именно постоянный ключ. Не включать prekeys без v2.
2. **Счётчик пересылок не подписан.** Курьер может изменить `hopCount`.
   v1 проверяет лишь его диапазон, а не доказанную длину пути.
3. **Совместимость проверки X25519.** Чёрный список Swift содержит
   нестандартные дополнительные представления, включая `00` × 31 `|| 01`.
   Их нужно сохранить при переносе и проверить отдельными примерами;
   заменять список только проверкой общего секрета нельзя молча.
4. **Отправка и приём текста различаются.** Отправитель обрезает пробелы,
   получатель проверяет только непустую строку и предел байтов. Это
   текущее поведение, а не разрешение переписывать принятый текст.
