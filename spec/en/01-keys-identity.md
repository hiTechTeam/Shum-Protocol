## 1. Three key pairs

A Shum identity contains three independent key pairs. All three are randomly created on first launch; **none is derived from another**.

| Key | Algorithm | Private | Public | Purpose |
| :--- | :--- | :--- | :--- | :--- |
| Noise | X25519 (Curve25519 Diffie–Hellman) | 32 bytes | 32 bytes | Noise sessions over Bluetooth and envelope sealing; determines Shum ID |
| Signing | Ed25519 | 32 bytes, RFC 8032 seed | 32 bytes | Card, profile, avatar seed and packet signatures |
| Nostr | secp256k1, BIP-340 Schnorr | 32 bytes | 32 bytes, x-only | Nostr event signatures and relay address |

The Nostr public key is also displayed as `npub` (Bech32 with the `npub` prefix), but travels in the protocol as 64 hex characters.

**Current iOS behavior:** keys are stored in Keychain:

| Key | Location |
| :--- | :--- |
| Private Noise key | `noiseStaticKey` |
| Private signing key | `ed25519SigningKey` |
| Nostr | Service `chat.shum.nostr`, key `nostr-current-identity`; JSON `{privateKey, publicKey, npub}`, with privateKey and publicKey in base64 |

A compatible client's storage format does not matter. Private keys must stay on the device.

### Ed25519 signatures are not deterministic

CryptoKit adds randomness to Ed25519 signing: signing the same data twice produces different 64-byte signatures. Both verify with standard RFC 8032 verification. Therefore:

- A compatible client **must** verify signatures, rather than compare their bytes.
- A compatible client **may** sign deterministically according to RFC 8032.
- Signature vectors check only whether the signature is valid.

## 2. Shum ID

Shum ID is a person's primary identifier in the protocol.

```text
shum_id = hex( SHA-256( noise_public_key ) )
```

- `noise_public_key` is the 32-byte public Noise key.
- The result is 64 lowercase hex characters.
- Code: `ShumContactCard.userID(_:)`, `ShumContactCard.id`.

The same function is also used for other inputs, such as profile bytes (`profileID` in section 02). Its code name is generic; Shum ID specifically means the hash of the Noise key.

## 3. Bluetooth peer ID

A peer with a known card is addressed in the Bluetooth mesh by its full Noise key:

```text
peer_id = hex( noise_public_key )        // 64 lowercase hex characters
```

Code: `ShumContactCard.peerID`, `PeerID(hexData:)`.

Bitchat also uses short 8-byte IDs (16 hex characters) within the mesh. They change over time and belong to the transport described in section 06.

## 4. Pixel avatar seed

Each identity has a pixel avatar rendered from a 64-bit seed. The default seed is derived from the Noise key:

```text
digest = SHA-256( "shum.pixel-avatar.v1\0" || noise_public_key )
seed   = UInt64 from digest[0..8], little-endian
```

- `"shum.pixel-avatar.v1\0"` is 21 bytes: ASCII text followed by a zero byte.
- The user can choose another avatar variant. Its seed is random and travels in the card's `avatarSeed` field.
- Rendering from the seed, including the generator, palette and rules, is a separate compatibility contract described in an appendix. The generator number travels in `avatarVersion`, currently `1`. A client must reject unknown versions rather than render an arbitrary result.

Code: `ShumPixelAvatarGenerator.seed(for:)`, `ShumPixelAvatarGenerator.version`.

## 5. Domain labels

Shum signatures prefix their data with a domain label. Currently known labels:

| Label | Bytes | Usage |
| :--- | :--- | :--- |
| `shum.pixel-avatar.v1\0` | 21 | Default avatar seed derivation, a hash rather than a signature |
| `shum.avatar-seed.v1\0` | 20 | Avatar seed signature |
| `shum.profile.v1\0` | 16 | Profile signature |

The card's `signature` has **no** domain label, a legacy of the first version; see section 02. This list will be extended with labels from sections 03 and 04.

## 6. Local storage key

The app has a fourth key: 32 random bytes for encrypting its local database (Keychain `shumStorageKey`, formerly `spotchatStorageKey`). It does not participate in the protocol and is never transmitted. It is listed here to distinguish it from identity keys.

## 7. Bitchat-derived Nostr identities

Bitchat has Nostr identities derived from a shared device seed for geohashes (`deriveIdentity(forGeohash:)`) and bridges (`deriveIdentity(forBridgeRendezvous:)`). They do not belong to Shum contact cards or conversations. Whether to document them is an open question.

## Questions

1. **Derived Nostr identities.** Are Bitchat geohashes and bridges used in Shum 1.0? If not, explicitly exclude them from v1.
2. **Noise/Nostr key association.** The keys are independent and associated only by the signed card. Bitchat also has a `nostr-noise-<base64>` Keychain mapping. Check whether Shum uses it.
3. **Key rotation.** Keys currently last for the profile's lifetime with no rotation. A leaked key requires a new profile. Record this for v2 together with ratcheting.
